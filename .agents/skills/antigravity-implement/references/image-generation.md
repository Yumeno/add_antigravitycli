## 1. Antigravity CLI での画像生成の仕組み [実測]

- 自然文で画像生成を指示すると、agy の内部画像生成ツールが自動で発動する。ツール名・モデル名は応答にもログにも出ない(agent は「画像生成ツール」としか言わない)。
- 手元検証時の内部モデルは nanobanana 2 系とみられるが、応答から機械的に確認する手段はない [推定]。**モデル名を報告させない・推測で書かない**(テキスト回答のモデル名フッター規則と同じ原則)。
- 実測では 1024×1024 の PNG(約 900KB〜1MB)が生成された。内部生成は JPG のことがあり、PNG を指定すると agent がローカルで変換して保存する(実測時は .NET の描画ライブラリで変換したと報告)[実測]。
- プロンプトの構造化(構図・照明・スタイルの詳細化)は agent が自動で行う。仕様書には要件だけ書けばよい [実測]。

## 2. 仕様書(タスク指示)の書き方

### 2.1 生成タスクの必須項目 [実測]

1. **ファイル名と形式**(例: `assets/hero.png`)
2. **保存先の絶対パス** — 最重要。次節参照
3. **被写体・内容**
4. **スタイル**(例: フラットデザイン、水彩、写真調)
5. **避けたい要素**(あれば)

### 2.2 保存先は絶対パスで明示する(最重要)[実測]

- 「このディレクトリ直下に保存」のような相対・曖昧な指定は、**agy の scratch ディレクトリ(`~/.gemini/antigravity-cli/scratch/`)に解決される**。wrapper が `--add-dir` で渡した workdir には入らない。
- scratch に落ちた生成物は**リポジトリ外なので Git 検収に映らない**(検収の盲点)。
- 対策: 仕様書に**リポジトリ内の絶対パス**を書く(例: `C:/path/to/repo/assets/hero.png`)。絶対パス指定であれば sandbox + `--add-dir` 下でも正しく書き込まれる [実測]。

### 2.3 編集タスクの指示形 [実測]

- リファレンス画像は**絶対パスをプロンプトに書くだけでよい**。wrapper の `-Attachment` / `--attachment` は不要(それらは VLM に「見せる」ための staging 経路。編集の入力参照はパス直書きで機能する)。
- **Change + Preserve の定式**が有効:
  - Change: 変更点を限定列挙する(「次の3点だけを変更」)
  - Preserve: 維持する項目を具体的に列挙する(「シルエットの形・ポーズ・位置、構図、スタイルは維持」)
- 実測では 3 点変更 + 維持列挙の指示で、被写体の形状・構図・スタイルを保ったまま指定箇所だけが変わった(identity preservation 良好)。
- 反復編集する場合、Preserve リストは**毎回再掲する**(前ターンの制約の自動継承を期待しない)[推定: 姉妹リポジトリ add_codexcli の公式裏付け知見からの横展開]。

### 2.4 未確認の上限値

参照画像の枚数上限・1 枚あたりのサイズ上限・プロンプト長上限・透明背景(アルファチャンネル)対応は、Antigravity CLI について**公式確定値が見つかっていない**。姉妹リポジトリ add_codexcli の数値(16枚 / 50MB / 32,000 文字 / 透明非対応)は **GPT-Image-2 固有であり流用しない**こと。必要になったら実機で段階的に確認する。

## 3. 検収(antigravity-verify との関係)[実測]

- 生成物は Git 検収で untracked binary として現れる。検収は「期待値照合型」ではなく「差分検出型(snapshot 比較)」なので、枚数・ファイル名が事前不明でも機能する。
- 実体確認は **magic bytes**(PNG は先頭 8 バイト `89 50 4E 47 0D 0A 1A 0A`)+ **バイト数** + **目視**。
  - 実測の正常生成は 1024px 級で約 900KB〜1MB。**数十 KB 未満なら placeholder を疑う**。
  - 目視を省かない。応答の「生成しました」報告と画像の実内容は別物として扱う。
- 出力先を**リポジトリ内の 1 ディレクトリに縛る**(2.2 のとおり、縛らないと scratch へ逃げて検収に映らない)。

## 4. 既知の注意点

- **agy のバージョン差**: 1.1.1 で `--print` の仕様が変わり、旧 wrapper が誤動作した(issue #7、修正済み)。上流 CLI は自動更新されるため、画像生成に限らず off-task な応答(依頼と無関係な CLI フラグの解説など)が返ったら、上流の仕様変更を疑って wrapper を最新化する。
- **失敗の形**: 生成失敗時に本文だけ返り、ファイルが作られないことがある。応答の報告パスと実ファイルの存在・バイト数を必ず突き合わせる。
- **時間**: 生成 1 枚あたり実測 30〜90 秒程度。`-Timeout` は 300 秒以上を推奨 [実測]。
